# Перенос просмотрщика на отдельный хостинг

Этот документ и утилита готовят перенос. Они не покупают домен, не создают
сервер, не меняют DNS и не переносят действующие данные автоматически.
Российское размещение само по себе не подтверждает соответствие системы
152-ФЗ: оператор отдельно определяет основания обработки, доступ и защиту.

## Что выбрать до переноса

- Отдельный HTTPS-домен или поддомен только для просмотрщика, например
  `https://viewer.example/pso/`. На этом **origin** (схема + имя + порт) не должны
  работать посторонние приложения. Разные папки одного домена не изолируют ключи.
- Серверную площадку и расположение основных БД, резервных копий и журналов,
  согласованные больницей. Это должно быть подтверждено условиями площадки,
  а не только названием доменной зоны или заявлением «российский сервис».
- Отдельные учётные записи публикации и управления сервером с многофакторной
  защитой, понятными владельцами, резервным доступом и ограниченными правами.
- HTTPS API, доступный телефону и больничному компьютеру, например
  `https://api.example/functions/v1/`. На ПК не требуется принимать входящие
  подключения или открывать больничную общую папку в интернет.

Публичная оболочка не содержит медицинские данные, но загружаемый ею код имеет
доступ к расшифровке на телефоне. Поэтому целостность публикации защищают наряду
с базой. Закрытые ключи нельзя публиковать или переносить этой утилитой.

## Подготовка копии сайта

В корне репозитория, Python 3.7 или новее, без дополнительных пакетов:

```sh
python3 scripts/configure-hosting.py --viewer-base https://viewer.example/pso/ --api-base https://api.example/functions/v1/ --output /absolute/path/pso-hosting-release
```

Вместо `example` укажите выбранные реальные адреса. Каталог результата должен
отсутствовать. Исходный `docs/` не изменяется; утилита не обращается к сети.

| Файл / каталог | Назначение |
|---|---|
| `docs/` | Копия сайта с адресами пяти API и точным `connect-src` |
| `service-config.json` | Публичные адреса для **нового** бота просмотрщика |
| `hosting.env.example` | Точный origin для `PSO_VIEWER_ORIGIN` на backend |
| `security-headers.txt` | Заголовки, которые настраивает владелец веб-сервера |
| `RELEASE.txt` | Адреса и напоминание, что публикация ещё не выполнена |

Публикуются только файлы внутри `docs/`, по пути из `--viewer-base`. Остальные
файлы служат настройке. Секреты и ключи администратора сюда не добавляют.

## Серверная часть

Текущая реализация использует Postgres, RPC и Supabase Edge Functions. Её можно
перенести в совместимое самостоятельное размещение Supabase; это отдельная
задача настройки инфраструктуры, а не запуск одного статического файла.
Нужны совместимый Deno runtime, HTTPS-доступ к PostgREST, необходимые
расширения Postgres и исходящие HTTPS-запросы к службам Web Push.
Модуль passkey закреплён на конкретной версии `@simplewebauthn/server`; проверьте
его требования к runtime по `device-auth-edge.ts` перед развёртыванием.

1. Разверните и проверьте совместимый backend. В закрытых настройках функций
   задайте `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY` и `PSO_VIEWER_ORIGIN`.
   Последнее — только `https://viewer.example`, без `/pso/`.
   Ключ `service_role` никогда не попадает в сайт, бот или этот репозиторий.
2. Для пустой базы примените базовые схемы по `DEPLOY.md`, затем схемы
   `device-auth-schema.sql` и `direct-schema.sql`. Для уже существующей базы
   изучите структуру и применяйте только необходимые изменения.
   Не запускайте повторно bootstrap администратора поверх рабочего состава.
3. Опубликуйте функции `pso-shortlinks`, `pso-push`, `pso-team`, `pso-direct`,
   `pso-device-auth` со всеми относительными зависимостями из `server/` и `docs/`.
   Они проверяют подписи устройств самостоятельно. CORS разрешает ровно
   согласованный origin; wildcard и отражение произвольного Origin недопустимы.
4. Обеспечьте периодический запуск предусмотренных SQL-функций очистки. Проверьте
   расписание в базовых/новых схемах на выбранной площадке. При истечении срока
   доступ закрывается независимо от выполнения фоновой очистки.
5. Подтвердите нового организатора по известному каналу и выполните закрытый
   bootstrap согласно `DEPLOY.md`. Новый публичный ключ организатора должен
   соответствовать ключу, созданному в приложении **нового origin**.
6. Создайте приглашения и подключите устройства заново. После проверки
   идентичности организатор подписывает допуски. До включения рабочих
   отправок используйте вымышленные фамилии и искусственные тестовые фотографии.

Смена API без смены origin может сохранить клиентские ключи, но перенос БД,
ролей, корневого доверия, подписанных допусков и push-подписок требует
контролируемой миграции. Не направляйте действующие клиенты на произвольный
пустой backend и не рассчитывайте на автоматическое восстановление доступа.

## Телефоны, старые сообщения и passkey

При смене origin браузер создаёт отдельное хранилище. Старые неэкспортируемые
закрытые ключи не переносятся. Старый значок и вкладка относятся к старому сайту;
установка нового значка — отдельное подключение. Passkey также привязан к
RP ID домена и на новом домене регистрируется заново.

Зашифрованное для старого ключа сообщение нельзя просто открыть новым ключом.
Для нужного случая отправитель создаёт новое сообщение новому утверждённому
получателю. Перенос не выдаёт новому телефону доступа к старым фото.
На период перехода сохраните прежнюю установку для контролируемого завершения
старых сообщений; после проверки отзовите старые устройства.

Новый бот хранит параметры отдельно от старого бота Пачки. Поместите
подготовленный `service-config.json` рядом с `pso_viewer.py` нового бота,
остановив его на время изменения настроек. Сохраните историю и закрытые
ключи, но заново подтвердите устройство и ключ организатора на новом backend.
Старый бот Пачки и его настройки этим действием не меняются.

## HTTP и эксплуатация

- `frame-ancestors 'none'` задаётся HTTP-заголовком, не meta-тегом.
  Остальной CSP разрешает только собственные скрипты и точный API origin.
- `index.html`, `manifest.webmanifest`, `sw.js` проверяются на обновление:
  используйте `Cache-Control: no-cache`, а не вечный immutable-кеш по прежним
  именам. Не отдавайте `sw.js` через перенаправление или HTML-страницу ошибки.
- HTTPS-страницы и service worker остаются на одном origin. Scope и ссылки
  относительные; не подменяйте scope на `/` для соседних приложений.
- Ответы API, включая ошибки, имеют `Cache-Control: no-store`. Не кешируйте их
  CDN и не записывайте request/response body в reverse-proxy, APM или debug-логи.
- Push содержит только непрозрачный ID и срок. Для iPhone используется служба
  доставки Apple; собственная БД не устраняет её участия. Фамилия,
  комментарий и фото не включаются в push.
- Push не подтверждает получение или осмотр. Во «Входящих» остаётся запись
  даже без уведомления. Новый бот в рабочие часы повторяет ожидающие
  оповещения; отдельно проверяйте этот процесс и очередь.
- Удаление из действующей БД не означает немедленного удаления из резервных
  копий. Их сроки и доступ определяют на площадке отдельно.

## Проверка перед переключением

На вымышленных данных проверьте оба направления, недоступность чужого сообщения,
отзыв устройства, замену телефона, повтор после сетевого сбоя, доставку push,
доступ через «Входящие» без push, скрытие содержимого при сворачивании, истечение
срока, фото, обновление установленной PWA и отсутствие открытых данных в логах.
Убедитесь, что старый и новый боты не используют одну базу состояния.

Без сведений о выбранном хостинге и домене этот перенос не считается выполненным.
